# Chutzpah VPN operations

Обезличенная документация по развёртыванию и эксплуатации Ubuntu VDS с 3x-ui, Xray, VLESS + TCP + REALITY, Caddy и Hiddify. Репозиторий содержит инструкции и пример inbound; автоматического деплоя здесь нет. `git clone` и `git pull` не устанавливают и не обновляют VPN.

**Актуализация: 2026-10-26, Europe/Moscow.** Проверены доступная сессия 25 октября, внутренний отчёт 19 октября и сохранённый клиентский конфиг 25 октября; сведения сопоставлены с текущими read-only проверками сервера и H2. Исходных сессий 19 октября в доступной локальной истории нет: для них источником служит отчёт, а не полный transcript. Неподтверждённые действия ниже явно отмечены.

IP, домены и URL целевых машин заменены заполнителями. `127.0.0.1`, `::1` — локальные адреса, `panel.example.net` — пример. Ссылки на официальные проекты и диагностические сервисы публичные. Реальные значения подставлять только локально, не сохранять в Git.

## 1. Фактическое состояние и расхождения с прежним README

| Компонент | Проверено 2026-10-26 |
|---|---|
| VDS / обозначение | `newvds`, Ubuntu 24.04 LTS, x86-64; адрес `<SERVER_IP>` |
| Панель | 3x-ui **3.10.2**, `x-ui.service`; backend `127.0.0.1:2053` |
| Серверное ядро | Xray **26.7.28**, запускается панелью; отдельная активная `xray.service` не требуется |
| Рабочий VPN | VLESS + TCP + REALITY, **TCP/13198**, `minClientVer=0.0.0`; в конфиге H2 flow `xtls-rprx-vision` |
| Прежние VPN-порты | TCP/443 и TCP/19744 **не слушаются**, но разрешения UFW для IPv4/IPv6 остались |
| Веб-панель | Caddy **2.11.7**, TCP/8443, Basic Auth перед входом 3x-ui; URL `https://<PANEL_DOMAIN>:8443/<PANEL_PATH>/` |
| Сертификат | TCP/80 слушается Caddy; текущий Caddyfile не содержит явного `disable_tlsalpn_challenge` |
| Подписки | В Caddyfile есть маршрут `/sub/*` к backend TCP/2096; 2096 слушается на wildcard-адресе, отдельного разрешения UFW нет |
| SSH | TCP/22, root по ключу доступен; **эффективно `permitrootlogin yes`, `passwordauthentication yes`**, `kbdinteractiveauthentication no` |
| Защита и обновления | UFW активен; Fail2ban активен, jail `sshd` и `3x-ipl`; `x-ui`, Caddy, Fail2ban и оба APT timer включены при загрузке |
| Время и reboot | `NTPSynchronized=yes`; `/var/run/reboot-required` присутствует, указан `libc6` |
| H2 | Ноутбук `belka`; Hiddify **4.1.1+40101** (Debian-пакет), конфиг формата sing-box; mixed proxy TCP/12334, redirect 12336, DNS direct 12337; входа 12335 в конфиге нет |
| Телефон | По подтверждению пользователя: 2026-10-26 VPN работает через офисный Wi-Fi и мобильную сеть; 2026-10-25 работал через домашнюю сеть |
| Сквозная проверка H2 | Запрос через явный HTTP-прокси `127.0.0.1:12334` успешен, внешний адрес совпал с VDS; адрес не публикуется |

**Исправлены прежние утверждения:** TCP/443 больше не является работающим inbound, TCP/19744 больше не является слушающим резервом, парольная SSH-аутентификация фактически разрешена. Смена VPN-порта и SNI видна в сессии/конфиге 25 октября; точные время, команды и причина серверного изменения в доступной истории не зафиксированы. Имя профиля с суффиксом `443` устарело: действующий порт определять по конфигу и listeners.

На 19 октября мобильный Hiddify 4.1.1 заработал после отката Xray и изменения `minClientVer`; отдельное подтверждение мобильного профиля TCP/443 тогда отсутствовало. Проверка H2 25 и 26 октября подтверждает настольный HTTP-прокси через TCP/13198. Дополнительно пользователь подтвердил работу телефона через этот VPN: 26 октября — через офисный Wi-Fi и мобильную сеть, 25 октября — через домашнюю сеть. Проверка телефона в этих трёх сетях подтверждена. Точный порт телефонного профиля отдельно не сверялся; TUN/TProxy на H2 и миграция остальных клиентов этим подтверждением не проверяются.

На H2 включены прямые исключения для `.br` и наборов `geoip-br`/`geosite-br`, остальной маршрут — `select`. Эти rule sets загружаются удалённо через `select`: загрузка зависит от работающего прокси и доступа к источнику. Поэтому даже успешный тест одного запроса не означает, что весь трафик идёт через VDS. Необходимость региональных исключений проверить отдельно; в этой задаче маршруты не менялись.

## 2. Зависимости и условия начала работ

- **VDS:** Ubuntu 24.04 LTS с systemd, root либо пользователь с рабочим `sudo`, доступ в консоль/rescue провайдера, исходящие DNS/HTTPS и доступ к официальным репозиториям. На рабочем сервере установка повторно не выполняется.
- **Сеть:** публичный адрес, корректные DNS `A`/`AAAA` для панели, доступный входящий TCP/80 для ACME HTTP-01; согласованные правила firewall провайдера и UFW. Если IPv6 не настроен, ошибочную `AAAA` удалить. DNS REALITY SNI и домен панели имеют разные назначения и не обязаны совпадать.
- **Порты:** заранее выбрать `<VPN_PORT>` и убедиться, что его не занимает другой процесс. Для текущего сервера это 13198; для чистого VDS в runbook пример 443. Панель Caddy использует 8443, backend панели — 2053; backend подписок — 2096, только если подписки действительно нужны.
- **Пакеты VDS:** `ca-certificates curl gnupg openssh-server sudo ufw fail2ban unattended-upgrades`, keyring-пакеты для Caddy. Для диагностики и приведённых далее команд — `python3 openssl dnsutils`; для просмотра установщика — `less`. Установщик 3x-ui может доустанавливать собственные зависимости: нужен рабочий APT и свободное место.
- **Рабочий компьютер:** OpenSSH client (`ssh`, `ssh-keygen`, `ssh-copy-id`), `curl`, `python3`; для портовых проверок — `netcat-openbsd`, для DNS — `dnsutils`. Hiddify нужен графический сеанс; Debian x64 пакет требует `amd64`, права на установку и доступные APT-зависимости. Для других архитектур/ОС выбирать соответствующий официальный asset.
- **Доступы:** отдельный SSH-ключ, проверка fingerprint сервера через независимый канал, менеджер секретов, два независимых входа (SSH и консоль), окно возможного простоя и место для зашифрованной копии вне VDS.

Значения `<SERVER_IP>`, `<PANEL_DOMAIN>`, `<PANEL_PATH>`, `<ADMIN_USER>`, `<VPN_PORT>`, `<REALITY_TARGET>`, `<REALITY_SNI>` подставлять перед запуском. Угловые скобки — обозначение заполнителей, shell воспринимает их как перенаправления. Блоки команд ниже рассчитаны на **Bash**; на H2 интерактивная оболочка может быть Fish, поэтому сначала выполнить `bash`. На VDS команды выполняются с `sudo`; root может выполнять их без этого префикса.

## 3. Последовательность деплоя на чистый VDS

Полные команды установки, конфиги и проверки по шагам — в [runbook](docs/deployment-runbook.md). Порядок обязателен; следующий шаг начинать после проверки предыдущего.

1. **Подготовить адреса и доступы:** консоль провайдера, DNS, SSH-ключ, приватный журнал версий/значений. Открыть у провайдера SSH, TCP/80, выбранный VPN-порт и TCP/8443; SSH/панель по возможности ограничить источниками администратора. Backend 2053/2096 не открывать.
2. **Проверить ОС, архитектуру, DNS и часы:** Ubuntu 24.04, `uname -m`, `timedatectl status`, `dig +short A <PANEL_DOMAIN>`, `dig +short AAAA <PANEL_DOMAIN>`. Проверить доступность TLS target REALITY с VDS. Разрешить проблемы сети, DNS и времени до настройки TLS/REALITY.
3. **Обновить ОС и поставить зависимости** из раздела 2/runbook. Если нужен reboot, согласовать окно, перезагрузить и проверить повторный вход до продолжения.
4. **Создать администратора и проверить ключ:** `adduser`, группа `sudo`, перенос public key; во втором терминале подтвердить SSH и `sudo -v`. Только затем отключать пароли/root по процедуре runbook, проверить `sshd -t`, эффективный `sshd -T` и повторный вход после reload. Это целевая настройка нового сервера; текущий VDS ей пока не соответствует.
5. **Включить UFW и security updates:** сначала разрешить фактический SSH-порт, затем TCP/80, `<VPN_PORT>` и 8443, после этого `ufw enable`. Проверить IPv4/IPv6 и firewall провайдера. Включить APT timers, определить политику автоматического reboot.
6. **Установить 3x-ui:** скачать официальный installer в root-only каталог, прочитать его, записать tag/версию и SHA-256, запустить сохранённый файл. `master`/`latest` подвижны; для повторения сохранить точные версии и артефакты. Проверить `x-ui.service`, backend listener, случайные учётные данные и web base path.
7. **Первую настройку панели выполнить через SSH-туннель:** `ssh -N -o ExitOnForwardFailure=yes -L 127.0.0.1:2053:127.0.0.1:2053 <ADMIN_USER>@<SERVER_IP>`, открыть локально `http://127.0.0.1:2053/<PANEL_PATH>/`. При занятом локальном порте выбрать другой только с левой стороны `-L`. Задать bind backend `127.0.0.1`, секреты сохранить вне Git.
8. **Установить Caddy:** официальный APT-репозиторий, сайт панели на 8443, неизменённый panel base path, Basic Auth с интерактивно созданным bcrypt hash, proxy на loopback:2053. Если VPN занимает 443, явно отключить TLS-ALPN challenge и использовать HTTP-01/80, как в runbook. Выполнить `caddy validate`, reload, проверить журнал, сертификат и оба уровня входа. Не публиковать `/sub/*` автоматически.
9. **Создать inbound:** VLESS, TCP/RAW, `<VPN_PORT>`, REALITY, совместимый TLS target/SNI, отдельные UUID, private/public key и short ID, flow клиента и сервера согласовать. Проверить listener и firewall. Исторический `minClientVer=0.0.0` отражает конкретную рабочую конфигурацию; выбор параметров для новой версии требует проверки совместимости. [JSON-пример](examples/vless-reality-inbound.example.json) — фрагмент серверной конфигурации, не клиентский профиль и не полный `config.json`.
10. **Установить Hiddify и импортировать профиль:** официальный пакет своей ОС/архитектуры, установка через APT на Debian/Ubuntu, импорт QR/ссылки по защищённому каналу. Сверить фактические port/SNI/UUID/flow/keys/short ID приватно. Изменения делать в профиле/панели: сгенерированный `current-config.json` перезаписывается приложением.
11. **Проверить Fail2ban:** включить `sshd` с systemd backend, проверить jail и эффективные actions; отдельный `3x-ipl` требует фильтра/action и журнала панели, одного названия jail недостаточно. Проверить автозапуск и внешние порты.
12. **Провести сквозной тест:** реальный запрос через явный mixed proxy Hiddify, затем телефон отдельно по Wi-Fi и мобильной сети. Сравнить выходной адрес с ожидаемым VDS приватно; проверить нужные приложения. Открытый TCP-порт и надпись «подключено» не заменяют передачу трафика.
13. **Сделать резервную копию и проверить восстановление:** согласованно сохранить SQLite/WAL, зашифровать, проверить расшифровку, вынести копию с сервера; отдельно сохранить конфиги Caddy/SSH/UFW, systemd drop-ins и версии/бинарные артефакты. При reboot повторить серверные и клиентские проверки.
14. **При миграции существующего сервера:** новый inbound сначала проверить на всех клиентах, затем убрать старый inbound и его правила из обоих firewall. Для текущего сервера старые listeners уже отсутствуют, но остались правила UFW. Не запускать шаги чистой установки поверх рабочего VDS.

## 4. Проверки работающей системы

На VDS, без изменения настроек:

```bash
sudo /usr/local/x-ui/x-ui -v
sudo /usr/local/x-ui/bin/xray-linux-amd64 version
caddy version
sudo systemctl is-active x-ui caddy fail2ban
sudo systemctl is-enabled x-ui caddy fail2ban apt-daily.timer apt-daily-upgrade.timer
sudo ss -lntup
sudo ufw status numbered
sudo fail2ban-client status
sudo fail2ban-client status sshd
sudo /usr/sbin/sshd -t
sudo /usr/sbin/sshd -T | grep -E '^(port|permitrootlogin|passwordauthentication|kbdinteractiveauthentication|pubkeyauthentication) '
timedatectl status
if sudo test -f /var/run/reboot-required; then
    sudo cat /var/run/reboot-required.pkgs
fi
```

Для SSH с `Match`-условиями дополнительно проверить `sshd -T -C user=<SSH_USER>,addr=<ADMIN_SOURCE_IP>,host=<CLIENT_HOSTNAME>`: общий вывод не описывает все условные ветви. Для текущего root-подключения с H2 проверка с `-C` также подтвердила разрешённые пароли. Вывод listeners, журналов и SSH-команд может содержать реальные адреса; перед передачей его обезличивать.

На внешней машине (после замены заполнителей):

```bash
nc -vz -w 5 <SERVER_IP> 22
nc -vz -w 5 <SERVER_IP> 80
nc -vz -w 5 <SERVER_IP> <VPN_PORT>
nc -vz -w 5 <SERVER_IP> 8443
nc -vz -w 5 <SERVER_IP> 2053  # ожидается отказ/тайм-аут
nc -vz -w 5 <SERVER_IP> 2096  # ожидается отказ/тайм-аут
```

Ограничение SSH/панели административным IP меняет ожидаемый результат с других сетей. Сканер портов не проверяет REALITY handshake. Для журналов: `sudo journalctl -u x-ui -u caddy -u fail2ban -n 100 --no-pager`; вывод держать приватно.

На H2:

```bash
pgrep -af hiddify
ss -lntup | grep -E ':(12334|12336|12337|17078)\b'
gsettings get org.gnome.system.proxy mode
gsettings get org.gnome.system.proxy.http host
gsettings get org.gnome.system.proxy.http port
gsettings get org.gnome.system.proxy.https host
gsettings get org.gnome.system.proxy.https port
```

`gsettings` относится к пользовательскому сеансу GNOME; для другой среды неприменим. Порт 17078 наблюдался в предыдущей сессии, его отсутствие само по себе не означает отказ mixed proxy. Порт 12335 не является обязательным. Наличие redirect/DNS входов в JSON не доказывает работающий TProxy/TUN.

Просмотреть только безопасные поля активного конфига, без адресов и ключей:

```bash
python3 - <<'PY'
import json
from pathlib import Path
config = json.loads((Path.home() / '.local/share/hiddify/data/current-config.json').read_text())
for item in config.get('inbounds', []):
    print('inbound:', item.get('type'), 'port:', item.get('listen_port'))
for item in config.get('outbounds', []):
    if item.get('type') == 'vless':
        tls = item.get('tls', {})
        print('VLESS port:', item.get('server_port'), 'flow:', item.get('flow'),
              'REALITY:', tls.get('reality', {}).get('enabled'))
PY
```

Сравнить прямой и проксированный выход, не печатая IP (нужны `curl`, Bash и доступ к диагностическому сервису):

```bash
direct_ip=$(curl --fail --silent --show-error --max-time 20 --noproxy '*' https://api.ipify.org) &&
proxy_ip=$(curl --fail --silent --show-error --max-time 20 --noproxy '' --proxy http://127.0.0.1:12334 https://api.ipify.org) &&
if [ "$direct_ip" = "$proxy_ip" ]; then
    echo 'Выходные адреса совпадают; проверить TUN/маршруты и ожидаемый адрес приватно'
else
    echo 'Выходные адреса различаются; сверить проксированный адрес с ожидаемым VDS приватно'
fi
```

`--noproxy '*'` отключает прокси curl, но не обходит системный TUN. `--noproxy ''` исключает обход явного прокси из-за `NO_PROXY`. Обычный `curl` может брать proxy из окружения и не проверяет настройки GNOME. Совпадение/различие адресов само по себе не доказывает правильность маршрута: при проверке 26 октября проксированный адрес отдельно сопоставлен с приватно известным адресом VDS.

## 5. Известные препятствия и действия

| Симптом / препятствие | Что проверить и сделать |
|---|---|
| SSH `Permission denied (publickey)` | Пользователя, выбранный ключ и `ssh-add -l`, права `.ssh`/ключа, серверный `authorized_keys`; при проблеме доступа использовать консоль. Не выводить закрытый ключ |
| `newvds: command not found` / не разрешается hostname | `newvds` — обозначение; SSH alias не создавался. Использовать `ssh -i ~/.ssh/id_ed25519 root@<SERVER_IP>` либо явно настроить `Host` в локальном SSH config. Fish не читает Bash aliases |
| SSH host key изменился | Проверить fingerprint через консоль провайдера; не отключать проверку ключа и не удалять запись вслепую |
| Тайм-аут TCP | DNS, IPv4/IPv6, listener, UFW, firewall провайдера, фильтры текущей сети. Проверить другую сеть; не менять одновременно SNI, порт и версию |
| Xray не запускается / `address already in use` | `ss -lntup`, журнал панели; развести Caddy и VPN по портам. Панель — 8443; при VPN/443 Caddy не должен занимать 443 |
| REALITY handshake timeout | Сверить профиль и inbound, часы, доступность target/SNI и TLS, UUID/flow/key/short ID, версию Hiddify/ядра. Успех отката на Xray 26.7.28 с Hiddify 4.1.1 исторический; универсальная совместимость не доказана |
| Hiddify показывает старые параметры | Обновить/повторно импортировать правильный профиль, выбрать его, переподключиться; проверить generated config. Метка профиля не определяет используемый порт |
| Панель 401 / login failed / 404 | Basic Auth Caddy и логин 3x-ui — два независимых набора данных; сверить их и точный base path, включая `/`. 404 вне разрешённого пути ожидаем; 401 на входе ожидаем без Basic Auth |
| Сертификат не выпускается/не продлевается | Публичный DNS, ошибочная AAAA, TCP/80, журнал Caddy и ACME challenge. При VPN/443 использовать HTTP-01 и отключить TLS-ALPN challenge; не обходить ошибку TLS флагом `-k` |
| Панель отвечает через tunnel, но не через Caddy | Проверить bind/порт backend, неизменённый base path, `caddy validate`, журнал и разрешения на Caddyfile; не использовать `handle_path`, удаляющий panel prefix |
| `/sub/*` доступен снаружи | Закрытый firewall backend 2096 не закрывает маршрут через Caddy/8443. Определить нужность подписок, защиту ссылок и судьбу маршрута отдельно |
| systemd sandbox запрещает запись | Проверить `systemctl cat x-ui` и drop-in `10-xui-sandbox.conf`, разрешённые пути и права. Не снимать все ограничения вслепую; полный override из старой сессии не восстановлен |
| После обновления VPN перестал работать | Вернуть сохранённую версию Xray поддерживаемым меню `sudo x-ui`/панелью и проверенный inbound; номера пунктов меню зависят от версии. Если артефактов/backup нет, воспроизводимый откат не обеспечен |
| Backup не восстанавливает весь VDS | `/etc/x-ui` сохраняет панель, но не Caddy/TLS, SSH, UFW, overrides и бинарники. Согласовать версии, права и пути; проверить распаковку и трафик на восстановленной системе |
| Не загружаются правила/DNS Hiddify | Проверить журналы приложения и доступ к remote rule sets; загрузка `geoip-br`/`geosite-br` идёт через `select`. Проверить профиль и DNS до удаления рабочих cache/настроек |
| Закрытый круг при отказе VPN | Скачать установщики/пакеты и сохранить SSH/консоль до изменения VPN. Рабочий VPN может быть нужен H2 для доступа к внешним репозиториям |

## 6. Доступы, backup и обслуживание

На H2 ключ по предыдущей проверке — `~/.ssh/id_ed25519`, public key — рядом с `.pub`, доверие к серверу — в `~/.ssh/known_hosts`. На VDS разрешённые root public keys находятся в `/root/.ssh/authorized_keys`. Ключ и парольная фраза не хранятся в Git; успешная подпись через ssh-agent не доказывает отсутствие парольной фразы.

Секреты панели и профили ранее сохранялись локально в `~/.config/3x-ui-production/`; наличие и актуальность конкретного файла проверять приватно. Также установщик может оставлять `/etc/x-ui/install-result.env`. Generated config Hiddify: `~/.local/share/hiddify/data/current-config.json`; это конфигурация клиента с секретами, а не серверный Xray config. Не использовать `cat` полного JSON или `.env` для публичной диагностики.

Перед изменением сохранить текущие версии, согласованную копию SQLite/WAL, Caddyfile, SSH/UFW и systemd overrides. Копирование только живого `x-ui.db` не гарантирует сохранность данных. Подробные команды архивации, шифрования и восстановления — в [backup guide](docs/configuration-and-backups.md). Остановка `x-ui` прерывает VPN и панель; окно простоя необходимо и для backup, и для reboot. Хранить копию вне VDS, шифровать и проверять расшифровку; полноценный disaster recovery требует отдельной проверки восстановления, которая в этой актуализации не выполнялась.

Менять одну существенную часть за раз, иметь SSH/консоль и способ отката. После обновления либо reboot повторить проверки раздела 4 и клиентский тест. Не обновлять автоматически Xray до проверки совместимости. `unattended-upgrades` в неактивном состоянии между запусками сам по себе не означает отсутствие security updates: проверять APT timers и журналы.

## 7. Оставшиеся действия

1. **SSH:** после проверки независимого доступа отключить парольную аутентификацию; определить политику root и отдельного sudo-администратора. Текущий `passwordauthentication yes` нельзя считать защищённой целевой настройкой из runbook.
2. **Старые порты:** подтвердить отсутствие зависимых клиентов, удалить ненужные правила TCP/443 и TCP/19744 в UFW для IPv4/IPv6 и у провайдера. Наличие listener и наличие firewall rule проверяются отдельно.
3. **Клиенты:** проверка телефона в офисном Wi-Fi и мобильной сети подтверждена пользователем за 2026-10-26, в домашней сети — за 2026-10-25; повторное подтверждение этих сценариев не требуется. При миграции сверить порт телефонного профиля и состояние остальных клиентов; TUN/TProxy на H2 проверять отдельно, если они нужны.
4. **Reboot:** согласовать окно, проверить резервный доступ и backup, перезагрузить, повторить проверки. Флаг `libc6` всё ещё присутствует; перезагрузка этой задачей не выполнялась.
5. **Панель/подписки:** определить ограничение источников TCP/8443, судьбу `/sub/*` и wildcard listener 2096. Ограничение панели не должно неожиданно сломать используемые подписки.
6. **Воспроизводимость:** сохранить точные установочные артефакты, конфиги/overrides вне Git и провести контрольное восстановление. Параметры firewall провайдера, корректность всех DNS/AAAA, внешний отказ backend-портов, текущий вход в панель и продление сертификата этой проверкой не подтверждались.

## 9. Правила публичного репозитория

Не коммитить рабочие IP/домены/URL машин, panel paths, credentials, UUID, REALITY keys/short IDs, подписки/QR, профили, базы SQLite/WAL, архивы, SSH keys, полные конфиги Xray/Caddy/Hiddify и `.env`. Локальный `private/` исключён из Git и содержит необезличенные материалы; не добавлять его через `git add -f`. При утечке ротировать данные доступа: удаление файла не удаляет историю и уже сделанные копии.

Перед коммитом проверять `git status --short`, `git diff`, `git diff --cached` и список отслеживаемых файлов. `.gitignore` не заменяет проверку содержимого. Коммит и публикация изменений выполняются отдельным действием.
